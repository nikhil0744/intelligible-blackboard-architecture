# Natural disagreement and a counterfactual intervention

Use `scripts.prototype_recovery`. This is a separate optional runner: the ordinary
`scripts.prototype_run` does not invoke recovery. Every starting contribution in
Ollama mode is generated by the live model; no starting debate is seeded and no
agent is instructed to disagree for the demonstration.

The runner starts with the reasoner, critic and verifier. After a real conflict,
it creates an isolated copy of the history before the disputed proposal. A fourth
agent, `counterfactual_resolver`, generates an alternative REVISE using the task
and observed criticism. Before each peer's first sandbox verification turn, the
runner asks that peer to solve the original question with all dialogue and leading
claims hidden. The reasoner derives the constraints, the critic builds likelihood
weights, and the verifier checks weighted worlds or posterior odds. Each peer then
sees its own calculation alongside the discussion and must check any disagreement
step by step. The independent answer is model-generated and can also be wrong;
it never uses evaluator references and is not forced onto the board.
The same independent checks run again before main-board confirmation.
Peers may revise the alternative if they find an error.
All three ordinary agents must explicitly ratify the same final proposal in the
sandbox. Only then is that exact proposal promoted to the main board, where
all three agents independently check it again. Promotion clears the old votes.
If a peer supplied the correction, the report preserves that peer as its author;
it does not credit the resolver with finding the corrected answer.

If they agree during ordinary discussion, there is no intervention. If sandbox
verification fails, the proposal is not promoted. If live verification fails,
recovery is not reported as confirmed. Correctness is graded separately after
inference; even an endorsed recovery can be incorrect.

## Questions to try

[challenging_tasks.json](../../examples/prototype/challenging_tasks.json) contains
five examples. They are designed to expose different reasoning mistakes, but
natural model disagreement cannot be guaranteed. The three roles use the same
Qwen model, so their mistakes can also be correlated.

| Task ID | Potential disagreement | Correct answer under the stated conditions |
| --- | --- | --- |
| `biased_host` | Applying standard Monty Hall odds versus conditioning on the biased host's observed door | `10/19` |
| `correlated_detectors` | Counting two copied detectors as independent evidence versus counting their shared observation once | `1/2` |
| `sampled_child` | Using the familiar “at least one Tuesday boy” puzzle instead of the specified random-child reporting mechanism | `1/2` |
| `two_envelopes` | Treating possible amounts without their specified prior versus conditioning on the observed envelope | `25` |
| `load_mix` | Comparing pooled success versus comparing rates within both load categories | `A` |

Start with `biased_host`, then try `correlated_detectors` or `sampled_child` if
the first case reaches ordinary agreement. Retain the runs where everyone agrees
too; selecting an interesting trace for a demonstration is different from
reporting an unbiased recovery rate. Do not raise temperature simply to claim
better recovery. A new seed is another run of the same question.

For the biased-host case, prize-in-door-2 has observation likelihood 1, while
prize-in-door-1 has likelihood 9/10. The posterior switch probability is
`(1/3) / ((1/3)*(9/10) + 1/3) = 10/19`. The evaluator references are kept in
`challenging_references.json`; they are never passed to agents.

## Use your existing Colab runtime

1. Finish or stop the current compute process.
2. Upload the newest `outputs/blackboard_prototype_source.zip` using the notebook's
   **Upload and verify the current source** cell.
3. Rerun **Install Ollama and configure one model**, then **Persist results and
   check inference** to refresh paths and check GPU readiness. The cached model
   is reused on the same runtime.
4. Add a new code cell containing the following. Run it instead of the ordinary
   **Start compute in the background** cell.

```python
# Requires ROOT, ENV and OUT_ROOT from the existing notebook setup.
import subprocess, sys, time, uuid
from datetime import datetime, timezone

TASK_ID = 'biased_host'  # also try correlated_detectors or sampled_child
SEED = 42
if 'COMPUTE_PROC' in globals() and COMPUTE_PROC.poll() is None:
    raise RuntimeError('Finish or stop the active compute run first.')
if 'DEMO_PROC' in globals() and DEMO_PROC.poll() is None:
    DEMO_PROC.terminate()
    DEMO_PROC.wait(timeout=10)
tag = 'recovery_' + datetime.now(timezone.utc).strftime('%Y%m%d_%H%M%S') + '_' + uuid.uuid4().hex[:6]
RUN_DIR = OUT_ROOT / tag
COMPUTE_LOG = OUT_ROOT / (tag + '.log')
command = [sys.executable, '-u', '-m', 'scripts.prototype_recovery',
           '--backend', 'ollama',
           '--tasks', 'examples/prototype/challenging_tasks.json',
           '--references', 'examples/prototype/challenging_references.json',
           '--task-id', TASK_ID, '--seed', str(SEED),
           '--trigger', 'first-conflict', '--require-gpu', '--out', str(RUN_DIR)]
with COMPUTE_LOG.open('w') as log:
    COMPUTE_PROC = subprocess.Popen(command, cwd=ROOT, env=ENV,
                                    stdout=log, stderr=subprocess.STDOUT)
for attempt in range(30):
    if (RUN_DIR / 'manifest.json').exists():
        break
    if COMPUTE_PROC.poll() is not None:
        raise RuntimeError(COMPUTE_LOG.read_text()[-8000:])
    time.sleep(1)
else:
    raise RuntimeError('No manifest; inspect ' + str(COMPUTE_LOG))
print('Artifacts:', RUN_DIR)
```

6. After completion, use the existing download cell. Open the new `demo.html`

## Command line

With Ollama already running and the same inference settings as the quickstart:

```bash
python -m scripts.prototype_recovery \
  --backend ollama \
  --tasks examples/prototype/challenging_tasks.json \
  --references examples/prototype/challenging_references.json \
  --task-id biased_host --seed 42 \
  --trigger first-conflict --require-gpu \
  --out outputs/presentation/natural-recovery-001

python -m scripts.prototype_demo \
  --run-dir outputs/presentation/natural-recovery-001
```

`first-conflict` intervenes after a live agent criticizes an existing proposal or
a different agent proposes a different answer. It is a proactive demonstration
policy, not evidence of a prolonged deadlock. `--trigger stall` instead waits for
three conflicting critiques by at least two agents on the active proposal.
Increasing the turn count cannot guarantee that a conflict will arise.

Limits cover the **whole run**: nine ordinary turns, up to six sandbox peer turns
and six live peer turns, up to three independent calculations before sandbox
checks and three more before live checks, 100 backend attempts including repairs/retries, and a
20-minute shared deadline. Preflight is accounted for separately. Exit `0` means
ordinary agreement or confirmed recovery; exit `2` includes unapproved recovery,
unresolved discussion, budget exhaustion or inference failure. Exit `1` is
preflight/internal/export failure and `130` is cancellation.

## What the viewer and records show

The viewer separates **Ordinary live discussion**, **Counterfactual alternative
in isolated sandbox**, **Sandbox peer verification**, **Sandbox proposal promoted
to live board**, and **Independent live confirmation**. Counterfactual posts have
a purple border, and the fourth role appears after its first visible post.
Sandbox turn numbers and main-board turn numbers belong to separate histories.
Checkpoint copies and promotion reuse model content; they do not count as new
model calls. The ordinary and counterfactual phases share one trial's usage.

`recovery.json` records the trigger, rollback point, sandbox approval, promotion,
the sandbox's final answer and proposal author, whether the resolver's original
proposal was endorsed, main-state hashes proving sandbox isolation, and live confirmation. `results.jsonl`
records independent correctness and the final main-board answer. Agreement after
a later main-board replacement is not counted as confirmation of the promoted candidate.
Raw requests/responses, failures, usage, CSVs, charts and saved replay are still
written incrementally or exported as in the ordinary prototype.
Independent calculations are recorded as `independent_analysis` events rather
than board contributions; their calls count under the `independent_verification`
usage phase. The current recovery prompt policy is
`prototype-recovery-v8-grouping-and-ratify` and the report includes the number of
independent checks. They reduce exposure to copied arithmetic errors but cannot
guarantee mathematical correctness from the shared model.

## Arithmetic and stale-vote checks

Numerical answers now require an evidence entry such as
`CALC: (1/3) / ((9/10)*(1/3) + (1/3)) = 10/19`. A bounded calculator
evaluates the numbers with exact fractions, using only `+`, `-`, `*`, `/` and
parentheses. Valid chains such as
`CALC: (1/3) / ((9/10)*(1/3) + (1/3)) = (1/3) / (19/30) = 10/19`
are supported, with every equality checked. A bare `CALC: expression` is also
accepted and evaluated before comparison with the numerical claim. Square grouping
brackets and Unicode `×`, `÷`, `−` are supported. It does not execute
model-generated code or read references.
It rejects false equalities such as `(1/3) / (19/30) = 1/19`, and rejects a claim
that differs from the last checked calculation. The model receives the exact
calculation result and must repair its JSON before it can post. This applies to
ordinary discussion, the resolver, private calculations, sandbox peers and live
confirmation. The viewer shows checked calculations on accepted contributions.
A RATIFY must restate the current proposal's already-checked claim, so it does not
need its own `CALC` entry; algebraic working in it is treated as a label, and any
numeric equality it states is still checked.

Ratifications must resolve to the current proposal through a valid endorsement
chain. Endorsing an old criticism or superseded proposal now causes a repair
request, rather than displaying a RATIFY that cannot count towards agreement.
Rejected attempts and repair reasons remain in the trace and usage accounting.
If repairs are exhausted, the turn fails and its invalid answer is never committed.
If live confirmation fails, the run still cannot claim confirmed recovery.

This is **calculator-assisted deliberation**. The checker verifies the expression
chosen by the model, not whether its assumptions correctly represent the question.
A correctly evaluated but inappropriate expression can still produce a wrong final
answer. Report this policy when comparing runs to earlier prompt-only versions.
The guards may also resolve an error before disagreement develops, in which case
the counterfactual resolver correctly stays inactive.

Earlier calculator versions rejected valid chains solely for having multiple
equals signs. The current version accepts valid chains and also audits adjacent
numeric equalities in labelled evidence, e.g. `P(H3) = 9/30 + 1/3 = 12/30`
is rejected because the sum is `19/30`. A final division using the incorrect
denominator cannot hide an earlier explicitly stated arithmetic error behind a
tautological check such as `CALC: 1/19 = 1/19`. Symbolic labels themselves are
not interpreted; assumptions and unreported intermediate steps still need model
reasoning and independent grading.

Compact fraction notation can also be disambiguated by the whole equality chain.
For example, `1/3 / (9/30 + 10/30) = 1/3 / 19/30 = 10/19` is accepted by
interpreting the middle step as `(1/3) / (19/30)`. At least one unambiguous
neighbouring expression must anchor the interpretation, and every step in that
numeric run must agree. The checker does not choose a grouping from the prediction
or reference answer. It records `fraction_operands_disambiguated_from_chain` and
the clarified expressions in contribution metadata; the viewer shows those
expressions under Calculator checks. Original model text is retained.
Bare ambiguous expressions must be parenthesized, and fully compact slash
sequences such as `1/3/19/30` retain standard left-to-right arithmetic rather
than guessing which slash separates the two fractions.

Older source bundles accepted only the resolver's original sandbox proposal.
They could report `sandbox_not_approved` even after peers corrected `2/3` to
`10/19` and endorsed the correction. Refresh the source ZIP and start a fresh
run to use the final-consensus promotion policy. Historical results are retained
as originally recorded. If the sandbox still lacks three endorsements, its
answer remains separate from the final main-board answer and is not promoted.

This is a bounded historical replay demo. The rollback point is the disputed
active proposal, and the alternative is informed by the actual observed criticism.
It does not run a paired no-intervention baseline, search many candidates,
establish causal credit, or implement the full distributed recovery daemon.
Present it as a live recovery workflow example, not proof of a measured causal
improvement. With `--backend mock`, every result is visibly labelled scripted.

The new path is regression-tested with mocked model outputs. Real T4 inference
and naturally occurring disagreement must be checked in your Colab runtime.
